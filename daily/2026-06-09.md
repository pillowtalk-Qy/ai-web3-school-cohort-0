目前项目仍然围绕这个核心问题：

```text
User says what they want
AI / Agent prepares an action
Wallet must verify what the user is actually about to sign
```

中文来说，就是用户用自然语言表达意图后，AI 钱包或 Agent 可能会生成链上操作，但签名前仍然需要一个清楚、可审查、不会过度暴露隐私的安全检查层。

今天的推进重点不是扩大功能，而是让第一版 Demo 更清楚：

- 用户输入一个 intent。
- Agent 生成或展示一个 proposed action。
- 系统解析交易 / Packet 的结构化事实。
- Guard 对比用户意图、交易事实和 policy。
- 页面展示风险判断、解释原因和人工确认入口。
- 最终留下一份 mock audit proof，证明这次审查发生过。

English companion:

Today was mainly a build day for the Vibe Coding hackathon project. The focus was not adding more scope, but turning the idea into a clear first Demo: user intent, proposed action, parsed facts, Guard review, risk explanation, human confirmation, and mock audit proof.

### Demo Scope / Demo 范围收束

今天继续确认第一版 Demo 应该保持窄范围。

暂时不把项目做成完整钱包，也不直接接入真实资产或真实签名流程。更适合黑客松第一版的是一个 pre-signing review surface：

```text
Intent
-> Proposed payment / transaction packet
-> Fact source
-> AI explanation
-> Policy check
-> Risk state
-> Human confirmation
-> Audit proof
```

这个范围能更好地展示项目价值：

- 用户看得懂自己要签什么。
- Agent 的提议不会直接绕过用户确认。
- AI 的解释不是凭空猜测，而是基于结构化事实。
- 风险判断有明确分类和理由。
- Demo 可以在 mock 环境里完成，不需要碰真实资产。

English companion:

The first Demo should stay narrow. It should be a pre-signing review surface, not a full wallet. This makes the problem easier to understand and keeps the Demo safer: structured facts first, AI explanation second, policy decision third, and human confirmation before any signing.

### Review Card Direction / Review Card 方向

今天把 `review card` 继续当成 Demo 的核心组件。

它需要同时服务两类人：

- 普通用户：快速知道这笔操作是否符合自己的意图。
- 评委 / 开发者：看清楚 Agent 如何做判断、依据是什么、哪里需要人工复核。

目前 review card 需要包含这些层级：

```text
1. User Intent
2. Proposed Action
3. Source of Facts
4. AI Explanation
5. Policy Decision
6. Risk Category
7. User Confirmation
8. Audit Proof
```

今天更明确的一点是：review card 不应该只是一个红色警告框。它应该是一条完整的审查路径，让用户看到系统为什么判断一致、为什么需要复核、或者为什么不建议签名。

English companion:

The review card should become the center of the Demo. It is not just a warning box. It should show the full review path: intent, proposed action, fact source, AI explanation, policy decision, risk category, user confirmation, and audit proof.

## Hackathon Direction / 黑客松方向

今天之后，项目方向更像一个可展示的安全审查 Demo，而不是一个抽象概念。

第一版 Demo 可以围绕 3 个样例展开：

```text
Case 1: Looks consistent
User asks for a limited action, and the proposed transaction matches.

Case 2: Needs review
The transaction can be parsed, but includes a risk such as broad allowance or unclear spender.

Case 3: Do not sign
The proposed action conflicts with the user's stated intent.
```

这三个样例足够展示项目的核心能力：

- 能处理正常路径。
- 能发现灰色风险。
- 能阻止明显不一致。

下一步更应该优先做这三条路径，而不是急着加入更多复杂 Web3 场景。

English companion:

The Demo direction is now more concrete: show three cases. One consistent action, one action that needs review, and one action that should not be signed. This is enough to demonstrate the product loop without overloading the first version.
